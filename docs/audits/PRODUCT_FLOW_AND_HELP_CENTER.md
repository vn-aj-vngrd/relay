# Product flow assessment and Help Center

Source-reviewed: 2026-09-05. Owner: Relay product and support.
Scope: the current working tree, public visitor through repeated saved game. This is a source-based product/process assessment, not observed user research, a security audit, or a claim that the new UI passed validation.

## Verdict

**The core flow is well-shaped, but not yet reliably self-explanatory for a first-time player or host.** Public planning and guest RSVP defer account creation until there is something worth keeping. One game carries the plan, players, live courts, repayment, and memories; repeat play reuses practical setup rather than replaying old participation. Those are strong foundations worth preserving.

The weak point is comprehension and recovery across boundaries: temporary versus saved play, invitation versus confirmed spot, publication versus discovery, and RSVP versus physical readiness. Some current controls contradict or hide those boundaries. A complete manual makes recovery possible and creates a durable reference for iteration, but **documentation is not an acceptable replacement for truthful confirmation, resilient drafts, visible pricing setup, or discoverable management controls**.

No P0 blocker is established by this bounded assessment. Priorities below rank potential harm, not measured frequency. There is no evidence here of actual conversion, abandonment, support volume, or task success rates.

### State distinctions that must survive future redesign

- Invite ≠ response; response ≠ Going; Going ≠ Here; Here ≠ current court assignment.
- Organizer role ≠ roster participation; co-host ≠ owner; lead organizer ≠ permission to delete.
- Publication ≠ Public visibility ≠ current Open games eligibility.
- Booking receipt/status ≠ player repayment proof; Proof sent ≠ Confirmed; Free ≠ Not set yet.
- Quick Play ≠ saved game; local Story background ≠ shared memory upload.
- Completion ≠ cancellation ≠ deletion. Deletion is irreversible; corrections do not reschedule history.
- `/games/[id]` and `/s/[slug]` remain two authorized access paths to the same game, not separate products.

## Help implementation and coverage inventory

### Architecture and route decisions

- Canonical landing `/help`; topic links `/help?category=<id>`; bookmarkable search `/help?q=<terms>&category=<id>`; each task `/help/<slug>`.
- `src/features/help/content.ts` is the typed, dependency-free authoring source. No CMS, HTML injection, backend writes, or new dependencies. Search includes category, title, summary, audience, prerequisites, steps, outcome, and troubleshooting; all whitespace-separated terms must match case-insensitively.
- Server-rendered index/results/articles keep the library out of a bespoke client search bundle. GET submit works without client-side search logic. Unknown category safely shows all topics; repeated query parameters are ignored rather than passed as unexpected array values. Unknown slugs use `notFound()` and a Help-specific recovery page.
- Help selects its shell from the server-verified session and existing profile completion state. Fully onboarded accounts use the normal **AuthenticatedAppShell**, preserving sidebar/account/navigation without Login/Signup prompts. Signed-out readers and missing/incomplete-profile recovery use **PublicProductShell** without creating a profile or redirecting to setup. Help disables mounting ApplicationTour; the shared shell defaults to existing tour behavior everywhere else, and explicit replay remains at `/home?tour=1`. Existing account restrictions still run for signed-in users. Only missing-session auth errors are treated as anonymous; other provider/database failures propagate. This supersedes the initial always-public-shell decision, which caused the reported authenticated-navigation regression. No auth/storage/proxy configuration or game permission changes.
- Original `/help#...` fragments cannot be server-redirected because fragments are not sent with requests. A compact native “Previous manual bookmarks” disclosure preserves all twelve unique original guide/reference/FAQ fragment targets and links to current articles, even when the index is filtered. The old duplicate `#payments` fragment has one canonical target.
- Reading uses incumbent typography, semantic surfaces, 1152px outer canvas, narrower 70ch article measure, numbered steps, restrained rows/dividers, category navigation and breadcrumbs. Steps are primary; prerequisites, outcomes, troubleshooting, and ownership metadata use labeled native disclosures, with secondary reference content alongside steps on wide screens. No preview dependencies or directory query block a help article. Existing preview source is left untouched but no longer mounted by the Help landing.
- Every article records audience, prerequisites, steps, expected outcome, troubleshooting, related slugs, source paths, shared owner, and a source-review date. Related links resolve within the library. Support endings expose the documented email and security instructions with safe-evidence limits; targets are not resolution promises.
- Public desktop Help is a separate support row immediately above the account prompt, not part of Try Relay; mobile navigation retains Help. Authentication form/confirmation/fallback headers retain a centered Brand without a Help link, per the requested final placement. Authenticated Help stays in the existing support navigation. `/help` is no longer excluded by robots, and canonical help URLs are included in the sitemap. No private game routes become indexable as a result.
